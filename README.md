# wb-mqtt-noolite

[Русский](README.md) | [English](README.en.md)

Служба wb-mqtt-noolite позволяет интегрировать устройства Noolite (пульты, выключатели и датчики) в контроллер автоматизации [Wiren Board](https://wirenboard.com/).
Это достигается за счет соблюдения [Wiren Board MQTT Conventions](https://github.com/wirenboard/conventions) и [WB-STD-001 «Идентификаторы MQTT-топиков в экосистеме Wiren Board»](https://github.com/wirenboard/wb-standards), а также использования адаптера MTRF-64, с помощью которого реализуется работа с устройствами Noolite(-F).
_Работа службы протестирована с адаптером [MTRF-64-USB-A](https://noo.by/adapter-mtrf-64-usb-a.html)._

**Функциональные возможности:**
* Прием управляющих команд от Wiren Board и передача их на исполнение устройствам Noolite
* Взаимодействие с адаптером NooLite MTRF-64, обработка ответов от устройств и публикация обновления статусов в MQTT.
* Опрос устройств Noolite(-F) по расписанию и отправка результатов в Wiren Board

> **Обновляетесь с версии 1.x?** См. раздел [«Обновление с версии 1.x на 2.0»](#обновление-с-версии-1x-на-20) ниже.

### Сборка под Wirenboard

Соответствие ревизии контроллера и цели сборки Go (`GOARCH`/`GOARM`):

| Контроллер | Процессор | Цель сборки | `GOARCH` | `GOARM` |
|---|---|---|---|---|
| Wiren Board 3.5 и старше | ARM926EJ-S | `armv5` | `arm` | `5` |
| Wiren Board rev. 6.3-6.6 | NXP i.MX 6ULL, Cortex-A7, 800 МГц | `armv7` | `arm` | `7` |
| Wiren Board 6.7 | NXP i.MX 6ULL, Cortex-A7, 800 МГц | `armv7` | `arm` | `7` |
| Wiren Board 7.4 | Cortex-A7, 4 ядра, 1.2 ГГц | `armv7` | `arm` | `7` |
| Wiren Board 8.5 | Cortex-A53, 4 ядра, 1.5 ГГц (64 бита) | `arm64` | `arm64` | — |

Все контроллеры на Cortex-A7 (rev. 6.3-6.6, 6.7, 7.4) собираются одной и той же командой — `GOARM` зависит только от набора инструкций процессора (ARMv7), а не от числа ядер или частоты. Отдельная цель сборки нужна только для Wiren Board 8.x, у которой 64-битный процессор Cortex-A53.

#### Через Makefile (рекомендуется)
```shell
make armv5     # Wiren Board 3.5 и старше -> build/armv5/
make armv7     # Wiren Board rev. 6.3-6.6, 6.7, 7.4 -> build/armv7/
make arm64     # Wiren Board 8.5 -> build/arm64/
make all       # все три цели сразу
make deb        # .deb пакеты для Debian 12/13 (armhf, arm64) -> build/deb/
make clean     # удалить build/
```
Каждая цель собирает оба бинарника (`wb-mqtt-noolite` и `mtrf_tool`) с одинаковыми флагами оптимизации (см. ["Оптимизация размера и памяти"](#оптимизация-размера-и-памяти) ниже). Про `make deb` подробнее см. [«Сборка .deb пакета (Debian 12/13)»](#сборка-deb-пакета-debian-1213) ниже.

#### Вручную (без Makefile)
```shell
# Wiren Board 3.5 и старше
CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=5 go build -trimpath -ldflags="-s -w" -o wb-mqtt-noolite-armv5 ./cmd/wb-mqtt-noolite

# Wiren Board rev. 6.3-6.6, 6.7, 7.4
CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=7 go build -trimpath -ldflags="-s -w" -o wb-mqtt-noolite-armv7 ./cmd/wb-mqtt-noolite

# Wiren Board 8.5
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags="-s -w" -o wb-mqtt-noolite-arm64 ./cmd/wb-mqtt-noolite
```
Замените `./cmd/wb-mqtt-noolite` на `./cmd/mtrf_tool`, чтобы собрать утилиту привязки устройств для того же контроллера.

## Оптимизация размера и памяти

Флаги сборки, используемые и в Makefile, и в командах выше:
- **`CGO_ENABLED=0`** — все зависимости проекта чистые Go, поэтому кросс-компиляция не требует ARM-тулчейна с C-компилятором, а бинарник получается полностью статическим (без зависимости от libc целевой системы).
- **`-trimpath`** — убирает из бинарника локальные пути файловой системы сборочной машины.
- **`-ldflags="-s -w"`** — убирает таблицу символов и отладочную информацию DWARF.

На связке этих трёх флагов бинарник `wb-mqtt-noolite` под armv7 уменьшается примерно с 12.4 МБ до 8.6 МБ (сборка без флагов оптимизации против сборки с ними), под arm64 — около 8.3 МБ.

Для ограничения потребления ОЗУ на слабых контроллерах (в первую очередь Wiren Board rev. 6.3-6.6/6.7 с NXP i.MX 6ULL) рекомендуется задать переменные окружения рантайма Go при запуске службы — доступны без пересборки бинарника:
- **`GOMEMLIMIT`** — мягкий лимит потребления памяти: сборщик мусора Go сам старается не превышать заданное значение (например, `GOMEMLIMIT=48MiB`).
- **`GOGC`** — доля роста кучи между циклами сборки мусора (по умолчанию 100 = куча может удвоиться перед следующим GC); меньшее значение (например, `GOGC=50`) снижает пиковое потребление памяти ценой более частого GC и небольшого роста нагрузки на CPU.

Оба варианта не требуют изменений в коде — их можно задать в `Environment=` unit-файла systemd (см. ниже, `packaging/wb-mqtt-noolite.service`) и подобрать по факту, глядя на реальное потребление (`systemctl status wb-mqtt-noolite`, `ps -o rss -p $(pidof wb-mqtt-noolite)`).

## Запуск как systemd-сервис

В `packaging/wb-mqtt-noolite.service` находится готовый unit-файл. Установка на контроллере (после того как бинарник собран под нужную цель и скопирован на устройство, например через `scp`):
```shell
install -m 0755 wb-mqtt-noolite /usr/bin/wb-mqtt-noolite
install -m 0644 packaging/wb-mqtt-noolite.service /etc/systemd/system/wb-mqtt-noolite.service
systemctl daemon-reload
systemctl enable --now wb-mqtt-noolite
```
Проверить состояние и логи:
```shell
systemctl status wb-mqtt-noolite
journalctl -u wb-mqtt-noolite -f
```

Unit-файл по умолчанию:
- перезапускает службу при падении (`Restart=on-failure`);
- задаёт `GOMEMLIMIT=48MiB` и жёсткий предел cgroup `MemoryMax=64M` — при необходимости уменьшите оба значения на слабых контроллерах (rev. 6.3-6.6/6.7) или увеличьте на более мощных (7.4/8.5), см. раздел выше;
- запускается от `root` для доступа к последовательному порту адаптера (`/dev/ttyUSB0`) без дополнительной настройки; альтернативный вариант (отдельный пользователь в группе `dialout`) описан комментарием в самом unit-файле.

## Сборка .deb пакета (Debian 12/13)

```shell
make deb
```
собирает бинарники (`make armv7`/`make arm64`) и упаковывает их в `build/deb/`:
```
wb-mqtt-noolite_2.0.0~bookworm_armhf.deb
wb-mqtt-noolite_2.0.0~trixie_armhf.deb
wb-mqtt-noolite_2.0.0~bookworm_arm64.deb
wb-mqtt-noolite_2.0.0~trixie_arm64.deb
```
Версия берётся из файла `VERSION` в корне репозитория. Бинарник статический (`CGO_ENABLED=0`), поэтому пакеты для bookworm и trixie идентичны по содержимому — суффикс `~bookworm`/`~trixie` в версии нужен только для того, чтобы оба варианта можно было одновременно держать в apt-репозитории с несколькими suite, а не потому, что для разных версий Debian требуется разная сборка. `armhf` соответствует цели `armv7` (Wiren Board rev. 6.3-6.6, 6.7, 7.4), `arm64` — Wiren Board 8.5. Отдельный пакет для `armv5` (Wiren Board 3.5 и старше) не собирается — такие контроллеры Debian 12/13 не поддерживают.

Собрать один конкретный пакет: `make deb-armhf` или `make deb-arm64`; собрать вручную под нужный suite напрямую (например, для другой версии): `packaging/build-deb.sh armhf bookworm build/armv7 2.0.0 build/deb`. Для сборки нужны только `dpkg-deb` и `fakeroot` (пакет `fakeroot` в Debian/Ubuntu) — полноценный `debhelper`/`dpkg-buildpackage` не требуется, так как пакет собирается из уже готовых бинарников, а не из исходников.

Пакет включает:
- `/usr/bin/wb-mqtt-noolite`, `/usr/bin/mtrf_tool`;
- `/etc/wb-mqtt-noolite.json` — конфигурация по умолчанию (порт `/dev/ttyUSB0`, брокер `127.0.0.1:1883`);
- `/etc/wb-mqtt-noolite-templates.json` — штатные шаблоны устройств (см. `templates/templates.json`);
- `/etc/wb-mqtt-noolite-devices.json` — **пустой список** `[]`, заполняется после установки;
- `/lib/systemd/system/wb-mqtt-noolite.service`.

Все три файла в `/etc` помечены как conffiles — при обновлении пакета dpkg не перезапишет молча ваши правки, а спросит, что делать (оставить свою версию / заменить на новую / посмотреть diff).

Установка на контроллере:
```shell
apt install ./wb-mqtt-noolite_2.0.0~bookworm_armhf.deb
```
После установки служба **не запускается автоматически** — `postinst` только перезагружает конфигурацию systemd и печатает подсказку. Перед первым запуском отредактируйте `/etc/wb-mqtt-noolite.json` и заполните `/etc/wb-mqtt-noolite-devices.json` (см. [«Список устройств (devices.json)»](#список-устройств-devicesjson) и [«Утилита mtrf_tool»](#утилита-mtrf_tool-привязка-и-отвязка-устройств)), затем:
```shell
systemctl enable --now wb-mqtt-noolite
```

## Конфигурирование и запуск службы
Служба wb-mqtt-noolite конфигурируется с помощью конфигурационного файла в json формате.
Основные параметры, которые необходимо передать: последовательный порт адаптера Noolite, реквизиты доступа к MQTT брокеру.
Также в секции device_config необходимо описать пути до отдельных JSON файлов шаблонов, описывающих модели устройств и самих устройства.
В каталоге templates находятся шаблоны. По мере развития проекта список будет пополняться.
В директории example приведен пример конфигурационного файла и списка устройств.

**Параметры командной строки:** -- config или -c с указанием пути до файла конфигурации службы

Пример конфигурационного файла:
````json
{
  "serial_port": "/dev/ttyUSB0",
  "timezone": "Europe/Moscow",
  "loglevel": "info",
  "mqtt": {
    "host": "127.0.0.1",
    "port": 1883,
    "username": "",
    "password": ""
  },
  "device_config": {
    "templates": "./templates/templates.json",
    "devices": "./example/devices.json"
  }
}
````

### Список устройств (devices.json)
Для работы службы требуется информация об устройствах, которые присутствуют в системе и описание шаблона модели устройства.
**Пример списка устройств:**
```json
[
  {
    "name": "Теплый пол",
    "noolite_type": "txf",
    "ch": 1,
    "template": "srf-1-3000-t"
  }
]
```
_**Здесь**:_
- **name**: Наименование устройства. Если задано - публикуется как `title` устройства в MQTT (см. ниже); если не задано - используется название модели из шаблона
- **noolite_type**: тип Noolite (TX, TX-F, RX, RX-F)
- **ch**: Канал, 1-63
- **address**: Может указываться адрес, но не обязательно
- **template**: Шаблон устройства

###  Шаблоны устройств (templates.json)
Шаблон устройств предоставляет информацию о моделях поддерживаемых устройств, их элементов управления и информацию о командах Noolite, которые будут передаваться в устройство.
Для выполнения определенных команд на регулярной основе реализована поддержка выполнения команд по расписанию. Расписание задается в формате crontab.
Шаблон описывается наименованием модели (`name`), локализованным названием (`title`) и набором элементов управления (`controls`).

Элементы управления имеют:
- **name**: идентификатор канала (сегмент топика `/controls/<name>`), формируется по правилам [WB-STD-001](https://github.com/wirenboard/wb-standards) (латиница в нижнем регистре, `snake_case`)
- **title**: локализованное название канала, объект вида `{"en": "...", "ru": "..."}`
- **type**: тип контрола, см. [Wiren Board MQTT Conventions](https://github.com/wirenboard/conventions). Для физических величин, не входящих в список стандартных типов (`switch`, `alarm`, `range`, `rgb`, `text`), используется generic-тип `value` совместно с ключом `units` (например, `"type": "value", "units": "deg C"`) — специфичные типы `temperature`/`rel_humidity`/`power`/`power_consumption` объявлены устаревшими
- **order**: порядок сортировки
- **readonly**: определяет будет ли возможность со стороны UI возможность изменять его значение
- **get_command**: команда, которая будет выполняться по расписанию, например: _"ReadState 0"_
- **set_command**: при поступлении команды на установку данного контрола - будет отправляться соответствующая Noolite команда
- **polling**: выполнять команду по расписанию?
- **polling_cron**: расписание выполнения команды указанной в get_command
- **min**, **max**: для типа range, минимальное и максимальное принимаемое значение
- **units**: единицы измерения (машинная форма по словарю Wiren Board MQTT Conventions, например `deg C`, `%`)
- **precision**: точность
- **dont_use_retain**: не использовать ретейн-значение из MQTT при восстановлении состояния после переподключения

Пример:
```json
{
  "templates": [
    {
      "name": "srf-1-3000-t",
      "title": {
        "en": "SRF-1-3000-T thermostat",
        "ru": "Термостат SRF-1-3000-T"
      },
      "controls": [
        {
          "name": "on",
          "type": "switch",
          "title": {"en": "Heating", "ru": "Нагрев"},
          "order": 1,
          "initial_value": "0",
          "readonly": false,
          "set_command": "SetSwitch"
        },
        {
          "name": "setpoint_t_ambient",
          "type": "range",
          "title": {"en": "Setpoint Temperature", "ru": "Заданная температура"},
          "order": 2,
          "min": 5,
          "max": 30,
          "initial_value": "23",
          "set_command": "SetTemperature"
        },
        {
          "name": "temperature",
          "type": "value",
          "units": "deg C",
          "title": {"en": "Temperature", "ru": "Температура"},
          "order": 3,
          "readonly": true,
          "get_command": "ReadState 0",
          "polling": true,
          "polling_cron": "*/1 * * * *"
        },
        {
          "name": "model",
          "type": "text",
          "title": {"en": "Model", "ru": "Модель"},
          "order": 4,
          "readonly": true
        },
        {
          "name": "address",
          "type": "text",
          "title": {"en": "Address", "ru": "Адрес"},
          "order": 5,
          "readonly": true
        }
      ]
    }
  ]
}
```

#### Поддерживаемые команды
У каждого элемента управления указываются команды, которые преобразуют MQTT сообщение в Noolite команду и обратно.\
**Поддерживаемые команды описаны ниже:**

|Команда|Описание и параметры|Пример|
|---|---|---|
|SetOn|Включить, не имеет параметров. |SetOn|
|SetOff|Выключить, не имеет параметров.|SetOff|
|SetSwitch|Включить или выключить, передается 1 или 0 соответственно.|SetSwitch|
|SetTemperature|Установить температуру (для srf-1-3000-t).|SetTemperature|
|ReadState|Запросить статус, параметр fmt (см.документацию на MTRF)|ReadState 0|

*Список команд будет расширяться.

## Структура MQTT-топиков

Служба публикует топики в соответствии с [Wiren Board MQTT Conventions](https://github.com/wirenboard/conventions) и [WB-STD-001](https://github.com/wirenboard/wb-standards).

Для устройства с типом `txf` и каналом `1` (`device_prefix` по умолчанию — `/devices/mtrf_`):

| Топик | Retain | Описание |
|---|---|---|
| `/devices/mtrf_txf_1/meta` | да | JSON `{"driver": "wb-mqtt-noolite", "title": {"en": "...", "ru": "..."}}` |
| `/devices/mtrf_txf_1/meta/error` | да | Флаг ошибки устройства: `r`/`w`/`p` либо пустая строка (ошибки нет) |
| `/devices/mtrf_txf_1/controls/<control>` | да | Текущее значение канала |
| `/devices/mtrf_txf_1/controls/<control>/meta` | да | JSON `{"type", "title", "units", "order", "min", "max", "precision", "readonly"}` |
| `/devices/mtrf_txf_1/controls/<control>/meta/error` | да | Флаг ошибки канала: `r`/`w`/`p` либо пустая строка |
| `/devices/mtrf_txf_1/controls/<control>/on` | — | Команда на изменение значения (публикуется клиентом/UI) |

Флаги ошибок (`meta/error`) — буквенные коды: `r` — ошибка чтения/связи с устройством, `w` — ошибка записи, `p` — пропущен период опроса. Пустая строка означает отсутствие ошибки.

## Обновление с версии 1.x на 2.0

Версия 2.0 приводит службу в соответствие с актуальной редакцией [Wiren Board MQTT Conventions](https://github.com/wirenboard/conventions) и [WB-STD-001](https://github.com/wirenboard/wb-standards). Изменения затрагивают только формат MQTT-топиков и файл `templates.json` — **`devices.json` менять не требуется**.

**Что изменилось:**
1. Метаданные устройства и каналов теперь публикуются одним JSON-топиком (`.../meta`, `.../controls/<c>/meta`) вместо набора отдельных под-топиков (`meta/name`, `meta/type`, `meta/order`, `meta/min`, `meta/max`, `meta/units`, `meta/precision`, `meta/readonly`) — старые под-топики больше не публикуются.
2. Устройство и каналы получили локализованные названия (`title`, en/ru) — до этого в MQTT публиковались только внутренние идентификаторы.
3. Топики `meta/error` теперь ретейнятся и используют буквенные коды ошибок (`r`/`w`/`p`) вместо произвольного текста.
4. Специфичные типы каналов `temperature`, `rel_humidity`, `power`, `power_consumption` заменены на generic-тип `value` с ключом `units` (эти типы объявлены устаревшими в Wiren Board MQTT Conventions).
5. Переименованы идентификаторы каналов в соответствии с каноном [WB-STD-001](https://github.com/wirenboard/wb-standards):
   - `value` → `temperature` (текущая температура `srf-1-3000-t`)
   - `setting` → `setpoint_t_ambient` (уставка термостата `srf-1-3000-t`)
   - `low_battery` → `alarm_low_battery`, тип `switch` → `alarm` (индикатор разряда батареи)

**Что нужно сделать:**
- Если используется штатный `templates/templates.json` из этого репозитория — просто обновите файл вместе с бинарником, никаких дополнительных действий не требуется.
- Если `templates.json` был скопирован и доработан самостоятельно (добавлены свои устройства/шаблоны) — прогоните его через конвертер `configconvert`:
  ```shell
  # предварительно сделайте резервную копию файла
  cp /etc/wb-mqtt-noolite-templates.json /etc/wb-mqtt-noolite-templates.json.bak

  go run ./cmd/configconvert -in /etc/wb-mqtt-noolite-templates.json
  ```
  Конвертер заменит устаревшие типы и идентификаторы каналов на канонические и выведет список внесенных изменений. Для каналов и шаблонов без `title` будет подставлена заглушка (равная идентификатору) — её нужно перевести/поправить вручную после конвертации.
- Если ваши автоматизации (wb-rules, дашборды и т.п.) явно ссылаются на топики `.../controls/value`, `.../controls/setting` или `.../controls/low_battery` — обновите их на новые имена (`temperature`, `setpoint_t_ambient`, `alarm_low_battery` соответственно), а также уберите зависимость от топиков `meta/name`, `meta/type` и прочих под-топиков `meta/*`, если они использовались напрямую.

## Утилита mtrf_tool: привязка и отвязка устройств

В пакет программ входит утилита `mtrf_tool`, которая позволяет напрямую отправлять команды на адаптер MTRF-64-USB-A: осуществлять привязку и отвязку устройств, устанавливать температуру и режим датчика термостата, включать/выключать нагрузку, читать статус.

### Сборка
```shell
go build -o mtrf_tool ./cmd/mtrf_tool
```

### Основные параметры
| Флаг | Описание |
|---|---|
| `-d`, `--device` | Последовательный порт адаптера, по умолчанию `/dev/ttyUSB0` |
| `-c`, `--channel` | Канал (ячейка привязки на адаптере), **1-63**. Значение `0` использовать нельзя — в `mtrf_tool` оно зарезервировано как признак «канал не указан» (при `--channel 0` утилита просто выводит справку) |
| `-m`, `--mode` | Протокол и направление: `tx`/`txf` — силовые блоки, которыми управляет адаптер; `rx`/`rxf` — выключатели, пульты и датчики, от которых адаптер принимает команды |
| `--command` | `bind`, `unbind`, `clear_all`, `on`, `off`, `status`, `status_output`, `thermostat_mode`, `poweron_state`, `temperature` |

**Важно:** канал, указанный в `mtrf_tool` (`-c`), должен совпадать со значением `ch` соответствующего устройства в `devices.json` — именно так служба wb-mqtt-noolite сопоставляет физически привязанное устройство с шаблоном и настройками конфигурации.

Ниже описаны сценарии привязки, основанные на руководстве по эксплуатации MTRF-64-USB-A (`docs/rukovodstvo-po-ekspluatatsii-mtrf-64-usb-a.pdf`, разделы 5-6) и коде `noolite/commands.go`.

### Привязка силовых блоков (TX / TX-F): реле, диммеры, розетки, термостат

Силовые блоки (реле, диммеры, термостат SRF-1-3000-T и т.п.) — исполнительные устройства, которыми управляет адаптер. Для них выполняется «ручная привязка» (руководство, §5.1):

1. Переведите силовой блок в режим привязки (обычно — удержание сервисной кнопки на блоке; точный порядок см. в инструкции на конкретное изделие).
2. Выполните привязку к свободному каналу, например 1, в режиме `txf` (nooLite-F) или `tx` (классический nooLite):
   ```shell
   ./mtrf_tool -d /dev/ttyUSB0 -c 1 -m txf --command bind
   ```
3. Об успешной привязке сигнализирует погасший светодиод на блоке; в логе `mtrf_tool` будет виден ответ адаптера с кодом `CTR=3` («привязка выполнена») и, для nooLite-F, 32-битным адресом устройства.
4. После подтверждения привязки `mtrf_tool` сам печатает готовый фрагмент для `devices.json` — остаётся скопировать его и заполнить `name` (адрес для nooLite-F в него уже подставлен, а `template` при известной модели устройства подбирается автоматически):
   ```json
   {
     "noolite_type": "txf",
     "ch": 1,
     "name": "TODO",
     "address": "00017526",
     "template": "srf-1-3000-t"
   }
   ```
   Модель определяется по ограниченному списку штатных шаблонов — если её не удалось распознать, `template` останется `"TODO"` и его нужно будет указать вручную.

Отвязка силового блока требует подтверждения на самом устройстве (нажатие сервисной кнопки, руководство §6.1/§6.2):
```shell
./mtrf_tool -d /dev/ttyUSB0 -c 1 -m txf --command unbind
```

### Привязка выключателей, пультов и датчиков (RX / RX-F): обработка нажатий

Пульты (PU212-2), датчики (PT111, WS1) и подобные устройства сами передают команды по радиоканалу — адаптер должен быть переведён в режим приёма и «слушать» канал ограниченное время (руководство, §5.3):

1. Включите привязку на канале, к которому будет привязано устройство, например 5, в режиме `rx` (классический nooLite — именно этот режим используется во всех штатных шаблонах `pt111`, `ws1`, `pu212-2`):
   ```shell
   ./mtrf_tool -d /dev/ttyUSB0 -c 5 -m rx --command bind
   ```
2. Адаптер переходит в режим ожидания на **40 секунд**. В течение этого времени нажмите сервисную кнопку/комбинацию на самом привязываемом устройстве (порядок ввода в режим привязки зависит от модели — см. инструкцию на изделие; как правило, это удержание кнопки до характерного мигания индикатора).
3. Если привязка не произошла за 40 секунд, адаптер автоматически выходит из режима ожидания — при необходимости повторите команду `bind`.
4. После подтверждения привязки `mtrf_tool` печатает фрагмент для `devices.json`, как и для силовых блоков (см. выше) — для классического nooLite адрес не определяется (протокол его не передаёт), поле `address` в сниппете отсутствует, а `template` нужно указать вручную.
5. **Дальнейшая обработка нажатий происходит полностью автоматически**: служба wb-mqtt-noolite получает от адаптера команды (включение/выключение, переключение, изменение состояния датчика, разряд батареи и т.п.) без каких-либо дополнительных действий и сразу публикует их в соответствующие топики `/controls/<control>` согласно шаблону устройства. Опрос по расписанию (`polling`) для таких устройств не требуется — именно поэтому в штатных шаблонах `pu212-2`, `ws1` и `pt111` он не используется. Подробнее о том, какие именно команды пультов поддерживаются, см. раздел [«Входящие команды от выключателей и пультов (RX)»](#входящие-команды-от-выключателей-и-пультов-rx) ниже.

Для устройств nooLite-F (`rxf`) руководство отдельно не описывает процедуру привязки, но по протоколу адаптера она аналогична — `MODE=3` вместо `MODE=1`, с той разницей, что в ответе адаптера присутствует 32-битный адрес устройства; `mtrf_tool` поддерживает этот режим (`--mode rxf`).

Отвязка (очистка одного канала) не требует подтверждения на самом устройстве (руководство, §6.4):
```shell
./mtrf_tool -d /dev/ttyUSB0 -c 5 -m rx --command unbind
```

Полная очистка памяти адаптера (все каналы сразу, руководство §6.5) выполняется без указания `-c` — работает только для режимов `rx`/`rxf`:
```shell
./mtrf_tool -d /dev/ttyUSB0 -m rx --command clear_all
```

## Входящие команды от выключателей и пультов (RX)

Кроме явных команд включения/выключения (`On`/`Off`), пульты и выключатели Noolite (например, PU212-2) в зависимости от того, как запрограммирована конкретная кнопка, могут присылать и другие команды протокола. Служба поддерживает:

- **Switch (переключение, CMD=4)** — кнопка не сообщает целевое состояние, а просто «переключает» нагрузку. Служба хранит последнее известное значение канала `on` и при получении `Switch` инвертирует его (`0↔1`), после чего публикует новое значение как обычно. Именно так можно повесить на один пульт единственную кнопку «вкл/выкл» вместо раздельных кнопок «вкл» и «выкл».
- **Load_Preset (вызов сценария, CMD=7)** — кнопка настроена на вызов записанного сценария/пресета. Значение публикуется в отдельный канал `preset` (добавлен в шаблон `pu212-2`) — это как раз тот случай, который удобно использовать как кнопку-триггер сценария в wb-rules (например, «ушёл из дома»/«пришёл домой», если на пульте запрограммированы разные пресеты на разные кнопки).

  ⚠️ Руководство MTRF-64-USB-A не документирует формат данных команды `Load_Preset` для пультов — в канал `preset` публикуется байт данных `D0` пакета "как есть". Что именно означает конкретное значение — зависит от того, как был запрограммирован пульт, и должно быть проверено опытным путём (посмотрите значение в MQTT при нажатии нужной кнопки) прежде чем завязывать на него автоматизацию.

Обе команды поддерживаются только в режиме `rx` (классический nooLite, как и весь остальной приём команд в этой версии службы) — для `rxf` формат данных не проверялся.
